## 一、本文解决什么问题

对标对象 **Instinct** 的核心命题是：**下一代 Agent 不是一个需要下载打开的新软件，而是一个拥有独立电脑、手机号与专属邮箱的虚拟超级个人**，退居幕后，通过短信 / 电话 / 邮件等既有渠道替人办事。

本文回答三件事：

1. Instinct 那套形态里，**哪些是普适规律**（必须吸收），**哪些是它的环境特解**（不能照抄）；
2. 我们的目标环境与它差在哪（差异变量），由此推出的**入口路线分歧**（我们做独立 App）；
3. 这套形态在我们这里会带来的**优势、劣势与不可逾越的警戒线**（含中国大陆法律框架约束）。

> **口径基线**：产品定位、服务对象、分销规则以 [product-vision.md](./product-vision.md) 与 [architecture-design.md §1](./architecture-design.md) 为准；本文不重复定义，只在需要处引用。

## 二、Instinct 形态要点提炼

> 以下为对访谈内容的**机制提炼**，非原文转述。左列为它的做法，右列为可迁移的**本质**。

| # | Instinct 的做法 | 可迁移的本质 |
|---|---|---|
| 1 | 不做独立 App、无网页端，AI 拥有独立虚拟电脑 / 手机号 / 邮箱，凭 iMessage、电话、邮件交互 | **消灭界面**：交互载体越接近用户既有习惯，学习成本越趋近于零 |
| 2 | 全天候**主动式（proactive）** 运行：自主唤醒、后台推演、在关键节点主动介入（如判断会议将迟到而主动叫车） | 主动性 = 从「执行指令」升级为「对结果负责」；被动一问一答只是极小部分 |
| 3 | **3 周信任拐点**：第 3 周约 40% 用户主动授权信用卡；一旦跨过门槛，该群体留存约 80% | 信任是**逐步授权**换来的；授权深度与留存强正相关，但必须用户可控、可随时撤销 |
| 4 | 与 Agent 核心逻辑**完全解耦的外部防火墙**：输入先筛查，每个行动与思维链在执行前另由独立系统审查、拦截或放行 | 行动型 Agent 的安全体系必须**独立于核心模型**，不能由被保护对象自我审查 |
| 5 | **受信任个人网络（trusted person network）**：Agent 之间直接交换受限数据（对齐日历、拼车），权限按对象细分配置；越权刺探即时向主人告警 | Agent-to-Agent 协作的前提是**关系维度的细粒度权限 + 滥用可感知**，而非二元好友关系 |
| 6 | 用户终身免费，向**供给侧**收交易抽成（take-rate），类比 Apple Pay / 运通；差旅占 50% 流水，内测期年化流水近 10 亿美元 | 变现点从「用户」移到「被分发的商家」；前提是掌握**超级分发权** |
| 7 | 算力焦虑：日环比 10% 复合增长 ≈ **每周算力需求翻倍**，而高阶算力交付周期数月，40% 精力用于算力规划 | 主动式架构的算力消耗是被动式的**数量级之上**（这是形态自带的成本结构，不是增长问题） |
| 8 | 不卷模型能力，卷**可理解性**与排版克制（倒金字塔、F 形视觉动线） | 能力同质化后，**交互质感与信息可读性**才是难复制的壁垒 |
| 9 | 零市场营销 + 邀请制内测控速（邀请码被炒到 300 美元） | 控速是为了守住可用性底线；增长本身不是问题，**能力跟不上增长才是** |

### 2.1 我们直接吸收的四条

1. **消灭学习成本**：交互载体贴近用户既有习惯（IM / 语音 / App 内一句话），而不是新增一套需要学习的界面。
2. **主动性要有，但要有打扰预算**：默认静默、分级触达（见 §六），主动性服务于「结果」，不服务于「存在感」。
3. **信任靠分级授权累积**：授权项可增量开放、可一键撤销；关键动作二次确认。
4. **安全体系与 Agent 核心解耦**：行动前审查不依赖核心模型自我约束。

### 2.2 我们明确不照抄的一条

**「不做独立 App、寄生既有渠道」在本土是高风险路线** ——理由与替代方案见 §四。

## 三、目标环境差异变量（我们 vs Instinct）

| # | 维度 | Instinct | 我们 | 设计含义 |
|---|---|---|---|---|
| 1 | 用户构成 | 海量陌生 C 端，邀请制获客 | **平台内部合伙人**（B 端身份、C 端行为习惯） | 无需冷启动教育；但产品必须**零学习成本**，不能给 B 端的管理后台负担（见 §五） |
| 2 | 流量来源 | 零营销 + 口碑裂变，需控速 | **平台自带流量**，随平台壮大而壮大 | 不需要「邀请制控速」；反而要提前设计**承载力**，避免平台增长时体验塌方 |
| 3 | 算力压力 | 日 10% 复合、供应链交付周期数月，是生死线 | **无用户过载的算力危机**（服务对象有限且确定） | 不必提前数月锁算力；但主动式仍会显著抬高单用户 token 消耗，需**成本上限与调度策略**（见 §九 警戒线 7） |
| 4 | 接口对接 | 逐个 OTA / 商户 / 航司 BD，摩擦大 | 平台内外接口相对统一，**对接更简单** | 可把精力从「接入谈判」转向「主动式编排质量」 |
| 5 | 变现 | 向供给侧收 take-rate，需从零建商户网络 | 生态内已有**分销 / 佣金 / 服务费**闭环 | 不必模仿 take-rate 叙事；变现走既有生态链路 |
| 6 | 入口 | **无 App**，寄生短信 / 邮件 / iMessage | **必须有自有 App** 作为聚合入口 | 关键路线分歧，见 §四 |
| 7 | 交互语言与载体 | 英文短信 / 电话 / 邮件 | 中文 IM（微信 / 企微）、语音、App | 渠道合规性差异极大（个人号自动化属违规区），见 §九 警戒线 |
| 8 | 合规框架 | 美国（相对宽松、以平台政策为主） | 中国大陆**强监管**（备案、个人信息、支付资质、内容标识） | 许多「产品上很优雅」的做法在本地不可执行，见 §九 |
| 9 | 信任起点 | 需 3 周逐步建立 | 合伙人**已有线下信任关系** | 信任拐点前移：授权阻力更低，但**滥用后果更严重**（破坏真实人际关系与生态），需更硬的技术边界 |

### 3.1 变体变量矩阵（同一系统、不同生态位的可配置项）

「有很多变体变量」的落法：把差异做成**配置**而非分支代码。

| 变量 | 可选值 | 影响面 | 归属 |
|---|---|---|---|
| 主动性档位 | 被动 / 半主动（建议式）/ 全主动（预执行 + 待确认） | 打扰频率、token 成本、信任风险 | 用户级设置 + 平台默认 |
| 触达通道 | App 推送 / 企微 / 短信 / 邮件 / 语音外呼 | 送达率、合规、被封风险 | 通道优先级配置 |
| 授权粒度 | 日历 / 文件 / 邮箱 / 位置 / 设备控制 / 支付 | 能力上限与隐私敞口 | 授权中心，逐项可撤销 |
| 支付参与深度 | 仅生成订单 → 用户确认后由持牌通道支付 | 是否触碰资金与牌照红线 | **平台级硬约束，不可配置放开**（见 §九） |
| 数据驻留 | 本地优先 / 云端 / 混合 | 隐私合规、可用性 | 平台级 + 用户知悉 |
| 打扰预算 | 每日主动触达上限、静默时段 | 留存与口碑 | 用户级，默认保守 |
| 生态位 | 合伙人类型 / 行业 | 分身与工具集差异 | 平台配置 |

## 四、路线分歧：入口与宿主策略

> 本章覆盖两个同源的决策：**入口放在哪**（§4.1–4.3）与**能力跑在哪**（§4.4–4.5）。二者在 Instinct 那里是同一套「轻资产 / 寄生」哲学的两面，在我们这里必须分别决策。

### 4.1 Instinct 的逻辑（寄生）

寄生既有渠道 → 零获客成本、无需教育用户、天然消灭界面。

### 4.2 我们的判断：入口主权不可外包

**核心论点：把「聚合用户」的能力寄托在别人的通道上，等于把命脉交给对手。**

| 通道 | 被切断 / 受限的现实风险 |
|---|---|
| 短信 | 通道需模板报备，内容与频次受运营商政策约束，营销类受限 |
| 电话外呼 | 外呼受骚扰治理约束，频次与场景有硬限制 |
| 邮件 | 送达率与进箱率不可控，且国内使用习惯弱 |
| 微信生态 | **个人号自动化属违规（外挂类），封号是常态**；只有官方开放接口（企微等）才是合规路径 |
| 第三方 IM / 平台 | 开放策略、接口权限、审核规则均可单方面变更 |

**结论**：任一通道失效不应等于主链路失效。因此——

- **App 是「入口主权」基础设施，不是可选项**；它承载身份、授权、回执、结果预览与一键撤销；
- **但不要求用户在 App 里做操作**。App 是「小钰」的门面与保险柜，不是又一个要学的软件；
- **通道降级为「触达冗余」**：App 为主，企微 / 短信 / 邮件 / 语音为可替换触达面，任意一条断掉只影响触达效率，不影响业务闭环；
- 需要配套**通道健康监控**（见 §九 警戒线 1）。

### 4.3 与 Instinct 的取舍对照

| 维度 | Instinct | 我们（本决策） |
|---|---|---|
| 入口 | 寄生外部渠道 | 自有 App + 外部渠道冗余 |
| 获客成本 | 极低（渠道自带） | 低（平台自带流量），但需承担 App 研发与维护 |
| 抗封禁能力 | 低（渠道断即断） | 高（有自有兜底入口） |
| 用户体验路径 | 无需下载 | 需安装一次，此后尽量不打开（只收结果与回执） |
| 工程成本 | 低 | 高（多端：App / 桌面端 / 服务端） |

> 这是**用工程成本换生存权**的取舍，符合「谁握入口谁握流量」的既有定位（[architecture-design.md §1.1](./architecture-design.md)）。

### 4.4 宿主策略：执行面外置、控制面集中

**决策**：以**寄宿用户电脑**作为执行面的首选宿主；Web / App / 远程控制器降为入口与兜底分支。**但这不是「系统以用户电脑为主体」** —— 准确表述是：

> **控制面集中（服务端），执行面外置（用户设备）。**

#### 为什么必须这样区分：已有实测分界线

渲染的落地经验给出了这条边界（[render-distribution-and-multi-tenant-scaling.md §5.3](../research/render-distribution-and-multi-tenant-scaling.md)）：

```text
纯本地：编译 HTML → Node / Chromium / ffmpeg 出 MP4
──────────── 分界线（store_render_output）────────────
必须服务端：账号解析(DB) → 落对象存储 → 建成品库 → 触发 ASR/视觉向量索引
```

**能外置的是「执行 / 算力」，永远不能外置的是「账号、存储、索引、记忆、编排、计费」。**

| 层 | 归属 | 内容 | 可外置 |
|---|---|---|---|
| 执行面 | 用户设备 | 视频渲染、OS 文件/回收站/快照、浏览器自动化、电脑控制（cua-driver）、**主动式常驻推演** | ✅ 首选宿主 |
| 控制面 | 服务端 | 账号与鉴权、对象存储、知识库入库与索引、记忆系统、编排与路由、A2A、分销与计费 | ❌ 永远不外置 |

#### 已有先例（已落地，非设想）

渲染已经是这条决策的完成版本，且验证了关键范式：

- 渲染**默认在用户本机执行**（桌面端 render worker，bridge `/render` + `/artifact`），吃用户 CPU；
- 云端 render worker **默认不启动**（compose `profiles: ["cloud-render"]`），服务端只处理轻量内容；
- 三级路由：**本机 bridge 优先 → 云端回退 → 明确报错**。

证据：[deployment-single-node.md §3](../deployment-single-node.md)、[modules/09-desktop-client.md §1a](./modules/09-desktop-client.md)。

#### 必须复用的降级判定规则

> **只有「通道不可用」（无注册设备 / 连不上 bridge / bridge 返回 401、502、503、504）才回退云端；「通道可用但业务失败」（缺二进制、脚本非法等）不回退，直接报错。**

这条规则是整个宿主策略的安全阀：它防止「本机为主」退化成「本机失败就静默降级」，从而把故障藏起来。

#### 成本账：省的是服务器算力，不是总成本

| 项 | 变化 | 说明 |
|---|---|---|
| 服务器 CPU / 内存 | ⬇️ 大幅下降 | 4C4G 单机部署下这是真金白银 |
| 客户端体积与分发 | ⬆️ | 渲染运行时实测约 500 MB（Chromium 338M + Node 121M + CLI 37M） |
| 可靠性成本 | ⬆️ | 设备休眠 / 关机 / 离线 / 性能差异 |
| 多端运维成本 | ⬆️ | 目前**仅覆盖 Windows**，Mac / Linux / 手机不覆盖 |

**在本项目环境下这个取舍明显更划算**：服务对象为内部合伙人，设备以长时间在线为主、数量可控、配合度高，不必面对 C 端的设备离线率。附带收益：数据留在用户本机，**个人信息不出域**，对 §九 合规警戒线是正向的。

#### 与主动式的协同（关键）

上一轮列入 §九 警戒线 7 的「算力 / 成本失控」——主动式常驻推演使 token 成本指数上升——**恰被本决策化解**：

- 主动式 Agent 天生需要**24 小时在线的宿主**；
- 用户电脑正是那个宿主；
- 常驻推演跑在用户设备上 → **平台侧算力成本趋近于零**。

「主动式」与「寄宿用户电脑」是一对天然匹配的决策，应当成对推进。

### 4.5 三端分工与远程控制器

| 分支 | 定位 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **用户电脑（桌面端）** | **执行宿主**（主） | 渲染、OS 操作、浏览器自动化、电脑控制、主动式常驻推演 | 不承担账号 / 存储 / 索引 |
| **Web** | **兜底入口** | 无设备时唯一的可用面；结果查看、授权、回执 | 无本机 worker，**不能**被当作「辅助」而裁剪 |
| **手机 App** | **入口 + 遥控端** | 一句话下达意图、接收回执与告警、远程触发电脑执行 | 跑不了 Python worker / cua-driver，**天生不是执行宿主** |
| **远程控制器** | 链路 | 手机 / Web → 电脑的任务下发与状态回传 | 见下方缺口 |

#### 缺口与进展（主链路阻断项）

| # | 缺口 | 状态 | 说明 |
|---|---|---|---|
| 1 | **设备「在线」状态不真实** | ✅ **已修复（2026-09-30）** | 原缺陷：`resolve_bridge` 仅筛 `status == "online"`，而该状态在 `register()` 时**直接置位**、无心跳维持，用户关机后服务端仍认为设备在线。已由**客户端心跳（60s）+ 服务端租约（180s）**修复，详见 [modules/09-desktop-client.md §1c](./modules/09-desktop-client.md) |
| 2 | **手机→电脑的远程控制通道未实现** | ⛔ 待补 | [modules/09-desktop-client.md](./modules/09-desktop-client.md) 标注手机→电脑的远程中枢长连接（WS 通道）**仍为「子项目 B」**；「远程控制器」这一环尚无实现，手机端目前只能作为入口而无法驱动电脑执行 |

> 服务端已有的 websocket / socketio 是**服务端 → 浏览器推送**用途，**不是**手机 → 电脑的中枢通道，二者不可混用。

## 五、面向 B 端用户的 C 端产品：设计含义

身份是 B 端（合伙人），行为习惯是 C 端（要一句话把事办了，不接受学习成本）。

| 原则 | 具体约束 |
|---|---|
| **一句话完成** | 用户表达意图即可，不做参数表单；缺信息时才追问，且追问要有默认值 |
| **默认值必须正确** | 宁可少做，不可做错；错误默认值的信任损耗远大于功能缺失 |
| **结果可理解** | 交付用倒金字塔：结论前置、排版克制，避免大段密集文本（吸收 Instinct 第 8 条） |
| **不做后台化** | 合伙人不需要先看仪表盘才敢用；配置与治理由平台侧承担 |
| **隐式留痕** | B 端属性要求可审计、可追溯、可导出，但这些是**系统能力而非用户操作负担** |

**反面清单（明确不做）**：
- 不给合伙人暴露模型选择、Agent 选择、工具选择等工程概念；
- 不把「学习我们的界面」当成用户的责任；
- 不以功能数量作为价值证明。

## 六、主动式 Agent 的落地要素

| # | 要素 | 说明 | 当前状态 |
|---|---|---|---|
| 1 | 常驻调度与自主唤醒 | 从「定时触发」升级为「事件 / 情境驱动触发」（日程临近、位置变化、IM 事件、文件变更） | ⚠️ 部分：定时任务（cron / 间隔 / 单次）已实现（`schedule_task_service.py`）；**事件驱动的自主唤醒未实现** |
| 2 | 打扰分级与打扰预算 | 静默 → 回执 → 推送 → 主动呼叫；默认静默，主动触达有每日上限与静默时段 | ⛔ 未实现（设计） |
| 3 | 授权中心与权限粒度 | 逐项授权（日历 / 文件 / 邮箱 / 位置 / 设备 / 支付），可一键撤销，授权变更留痕 | ⚠️ 部分：RBAC 与工具凭证治理已存在（`docs/rbac.md`、`tool_credential_resolver.py`）；**面向终端用户的授权中心未实现** |
| 4 | 行动前审查（独立于核心逻辑） | 破坏性 / 对外发送 / 资金类动作，执行前经独立策略层校验与放行 | ⚠️ 部分：工具治理与风险分级已存在（[extensibility-design.md](./extensibility-design.md)）；**独立审查面未成形** |
| 5 | 受信网络与 A2A | 合伙人之间按关系维度配置权限，越权即告警 | ⚠️ 底座已有（`a2a_gateway_service.py`、`public_agent_a2a_service.py`）；**关系权限与越权告警未实现**（[04-social-creator.md](./modules/04-social-creator.md)） |
| 6 | 记忆与偏好沉淀 | 偏好一次表达即长期复用，可泛化到新场景 | ⚠️ 记忆系统已实现（`docs/prd/memory-system/`）；主动式调用链路未打通 |
| 7 | 可理解性 | 结论前置、排版克制、可预判下一步 | ⛔ 未实现（设计） |
| 8 | 可回滚兜底 | 任何破坏性操作均可回滚（改坏回滚、删错找回） | ✅ 已实现（回收站 + 快照） |

> **接线提醒**：§六 中标 ⚠️ 的项，是「底座已存在但主动式链路未接入」，不可当作「已实现」对外表述。

## 七、优势

1. **信任起点高、拐点前移**：合伙人与平台已有线下关系，无需 3 周冷启动；授权阻力更低。
2. **流量自带、无冷启动焦虑**：不需要邀请制控速，可以把精力放在体验而非获客。
3. **无算力供应链死亡风险**：服务对象有限且确定，不必提前数月押注算力。
4. **接口对接成本低**：平台内外接口相对统一，接入不需要逐个商务谈判。
5. **变现闭环已在生态内**：分销 / 佣金 / 服务费体系已实现，不必从零搭建供给侧网络。
6. **双壁垒**：线下供应链矩阵（短期无法追赶）+ 线上数字资产与用户生态（无法被抄走）。
7. **B 端付费与配合度**：合伙人比陌生 C 端更愿意配合授权与流程，主动式能力更容易发挥。

---

## 八、劣势与风险

> 优势多来自「我们是平台内部的一环」，风险也正来自同一处。

| # | 劣势 / 风险 | 说明 |
|---|---|---|
| 1 | **外部世界覆盖有限** | Instinct 的「替你在全网办事」我们做不到：生态相对封闭，站外 OTA、政务、线下服务受接口与合规限制 |
| 2 | **单用户固定成本摊不薄** | 用户量小，主动式推理的固定开销（常驻推演、批处理）缺少规模摊薄，单用户成本可能高于 C 端大厂 |
| 3 | **角色冲突口径** | 平台方同时是服务提供方，抽成 / 推荐易被质疑「既当裁判又当运动员」 |
| 4 | **体验方差大** | Instinct 输出统一体验；我们面对的是水平参差的合伙人群体，产品口碑取决于最差那一环 |
| 5 | **做 App 的成本与冷启动** | 与 Instinct 相反的取舍：需要多端研发与维护，还要让合伙人愿意装 |
| 6 | **主动性 ≠ 价值** | 过度打扰会直接摧毁信任；且 token 成本随主动性**指数上升**（参见 §九 警戒线 7） |
| 7 | **合规成本高** | 生成式 AI 备案、算法与内容标识、个人信息保护、支付资质，任一环节缺失都可能致命（见 §九） |
| 8 | **部署规模上限** | 单机 / 小规模部署存在资源上限（见 [deployment-single-node.md](../deployment-single-node.md)），主动式常驻任务会加剧内存与算力超卖风险 |

## 九、警戒线（红线清单）

> 每一条都给出**触发信号**，便于早期识别；红线类（不可配置放开）单独标注。

| # | 警戒线 | 触发信号 | 后果 | 应对 |
|---|---|---|---|---|
| 1 | **渠道单一依赖**（红线） | 主链路依赖某一家 IM / 短信 / 邮件通道 | 通道被切断 = 断手断脚 | 多通道冗余 + 自有 App 兜底 + 通道健康监控；不把任何单一外部通道写进主链路 |
| 2 | **未经授权代持 / 代付资金**（红线） | 系统内出现「用户余额 → 平台代付」的资金池 | 触碰非银行支付机构监管与「二清」红线 | 只做**指令下发 + 用户确认 + 持牌通道结算**，平台不经手资金；临界业务做合规评估后再上 |
| 3 | **敏感个人信息过度收集** | 收集金融账户、行踪轨迹、生物识别等未单独同意 | 违反《个人信息保护法》 | 分级授权 + 单独同意 + 最小必要 + 一键撤销 + 全程留痕 |
| 4 | **自动化决策无人工干预** | 对用户权益有重大影响的决策完全自动执行 | 自动化决策透明度与拒绝权要求 | 关键动作（支付、对外发送、删除）必须二次确认或可拒绝 |
| 5 | **A2A 越权刺探** | 受信网络中出现超出授权范围的访问 | 破坏真实信任关系与生态 | 关系维度权限硬隔离 + 即时告警 + 审计留痕 |
| 6 | **打扰过度** | 用户关闭通知、卸载、明确表达反感 | 信任与留存断崖 | 打扰预算、静默时段、默认静默；主动性可降档 |
| 7 | **算力 / 成本失控** | 主动式常驻任务 token 消耗指数增长 | 成本不可控，商业模式失效 | 主动性档位限流 + 空闲时段调度 + 缓存命中优先 + 批处理离线化 + 单任务预算上限 |
| 8 | **依赖未备案 / 不合规的第三方接口** | 接入了无资质或政策易变的服务 | 连带合规风险与随时中断 | 供应商合规准入清单，禁止接入违规通道 |
| 9 | **个人号自动化操作**（红线） | 用非官方方式驱动个人社交账号 | 违规封号、账号损失 | 只走官方开放接口（企微等），禁止外挂式自动化 |
| 10 | **内容与数据出境** | 数据流向境外模型 / 服务 | 《数据安全法》《个人信息保护法》出境要求 | 数据分类分级，出境场景先评估 |
| 11 | **AI 生成内容未标识** | 生成内容对外发布但无标识 | 《人工智能生成合成内容标识办法》要求 | 生成内容统一标识与元数据留存 |
| 12 | **破坏性操作不可回滚** | 任一次误操作导致用户数据不可恢复 | 用户信任直接崩塌 | 保持「回收站 + 快照」为强制前置能力，任何新破坏性动作必须挂兜底 |
| 13 | **文档与宣传口径越界** | 把设计稿写成「已实现」，把试点写成「已上线」 | 误导合伙人，合规与商誉风险 | 落地状态一律以 §十一 / 代码证据为准（遵守 AGENTS.md 架构文档同步规则） |
| 14 | **设备在线状态失真**（红线） | 设备关机 / 休眠后服务端仍判定为 online，任务派给死设备 | 主链路故障（详见 §4.5） | ✅ 已落实（2026-09-30）：心跳 60s + 租约 180s + 读时降级。后续任何新增的设备状态来源都不得绕过租约判定 |
| 15 | **静默降级** | 本机失败被悄悄回退云端，故障不可见 | 问题被掩盖，成本失控 | 沿用渲染范式：只有「通道不可用」才回退，「业务失败」直接报错（见 §4.4） |
| 16 | **外置边界被误读** | 以「本机为主」为由裁剪服务端控制面 | 账号 / 存储 / 索引 / 记忆 / 编排 / 计费的权威性被破坏 | 边界写死（见 §4.4 边界表），任何外置动作先核对分界线 |
| 17 | **平台覆盖缺口被忽略** | 默认所有用户都装了桌面端 | 未装客户端 / 非 Windows 用户无可用路径 | 保留 Web 兜底入口与云端回退；覆盖范围（当前仅 Windows）必须在文档与宣传中声明 |

### 9.1 国内外水土差异的根因

| 维度 | 海外（Instinct 环境） | 中国大陆 |
|---|---|---|
| 渠道 | 短信 / 邮件 / iMessage 开放且稳定 | IM 生态封闭，个人号自动化违规，线上触达受限 |
| 数据 | 以平台政策与企业自律为主 | 法定的个人信息保护、数据分类分级、出境评估 |
| 支付 | 卡组织体系成熟，代理支付摩擦小 | 需持牌经营，代收代付有明确红线 |
| 内容 | 事后追责为主 | 生成式服务需备案，生成内容需标识，事前准入 |
| 用户预期 | 偏好「无 App」的轻交互 | 习惯「有 App 可查、可申诉、可撤销」 |
| 信任 | 需时间建立 | 关系驱动，信任来得快，但破坏后果更重 |

**一句话**：Instinct 是在「渠道开放 + 事后监管」的水土里做「消灭界面」；我们是在「渠道受限 + 事前准入」的水土里，必须**先有入口主权与合规底座，再谈消灭界面**。

| # | 问题 | 影响 |
