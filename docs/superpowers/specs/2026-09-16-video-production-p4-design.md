# 视频制作与知识库 P4 设计（分层抽帧 + HyperFrames 统一渲染）

> **状态**：需求已逐项确认，设计待评审。
> **日期**：2026-09-16
> **主文档**：[knowledge-base-product-form-design.md](../../prd/knowledge-base-product-form-design.md) | [02-knowledge-base.md](../../prd/modules/02-knowledge-base.md) | [08-os-automation.md](../../prd/modules/08-os-automation.md)
> **调研依据**：[hypit-and-hyperframes-evaluation.md](../../research/hypit-and-hyperframes-evaluation.md)（非权威）

## 1. 背景与目标

知识库 P1–P3 已落地（素材入库 → 多模态解析 → 检索取料）。P4 要解决的是**「改细节」与「出片」**：

- 用户说「把第 3 个视频讲产品卖点那段改一下」——需要**能定位到确切片段**，并执行裁剪 / 拼接 / 加字幕。
- 用户想做新视频——**以真实素材为主干，中间插入 AI 生成的过场/一致性素材**，最终编排成片。

调研了开源项目 Hypit（复刻爆款视频的 Agent 工作流引擎）后确认两条可借鉴思路：

1. **语义锚定**：素材绑在「台词/片段」上而非时间轴上——改一句台词，挂它的镜头/字幕/音轨一起走。
2. **代码渲染**：视频写成结构化文本，由渲染引擎编译成片，Agent 改文本即改视频。

**关键结论**：Hypit 本身**不可直接集成**（其许可明确禁止多租户 SaaS 与白标），但其渲染后端 `@hypit/render-hyperframes` 依赖的 **HyperFrames** 是 HeyGen 开源的**标准 Apache-2.0** 项目，无多租户限制。因此本设计**不引入 Hypit 任何代码**，仅借鉴其设计思想，并以 HyperFrames 为渲染引擎。

**目标**：让知识库从「素材仓」升级为「素材仓 + 内容取料台 + 成片产出线」，且成本可控、配额可对账。

## 2. 已确认的设计决策

| 议题 | 决策 |
| --- | --- |
| 渲染引擎 | **HyperFrames**（HeyGen，Apache-2.0），不引入 Hypit 代码 |
| 架构 | **编/生/渲三层**，一份 HTML composition 同时承载真实素材、AI 补素材与代码渲染 |
| 画幅 | **竖屏 9:16 与横屏 16:9 都要支持**（`data-width` / `data-height`），不写死 |
| 语义锚定 | 落在 HTML 容器层级：一个 segment = 一个容器，镜头/字幕/音轨挂其下 |
| 渲染宿主 | **专用渲染 worker + 独立 `render` 队列 + 显式 `-Q` 隔离** |
| 成品去向 | **入知识库**，进**系统预置的成品库** |
| 成品库形态 | 每用户**系统预置唯一**成品库（`created_from` 标识），与零散素材彻底分开 |
| 成品库手动上传 | **禁止**（它是渲染产物的专用仓，混入手传素材即失去「成品」语义） |
| 用户传完整视频 | 允许，但**以素材身份入视频库**，不是成品 |
| 成品配额 | **吃容量**（与普通文件同口径） |
| 素材上传配额 | **严格**：素材大小 + 解析预留 > 剩余 → 拒绝并提示扩容 |
| 成品入库配额 | **宽让**：允许溢出，但**仅当剩余 > 0**；恰好 0 也拒绝 |
| 溢出后行为 | 立即超额，后续上传全拒；扩容后溢出部分直接吃掉新容量（网盘式） |
| 解析产物计费判据 | **持久化留存的计入配额；用完即删的不计** |
| L1 抽帧 | **动态**：随时长对数增长，下限 6 帧、**1 小时触顶 60 帧** |
| L1 抽帧分布 | **全片均匀**（现状是只取开头 3 帧，属缺陷） |
| 帧时间戳 | **新增 `metadata.time_offset`**（补上设计稿 §4.2 一直缺失的定位能力） |
| L2 触发 | **只对检索命中区间密集抽**，不重扫全片（L1 是粗地图，L2 是放大镜） |
| L2 密度 | 命中区间内**每 0.5 秒 1 帧** |
| L2 区间来源 | **自动从检索命中推导（默认）+ 支持显式指定**（A+B） |
| L2 单次窗口上限 | **600 帧**（= 5 分钟），超出提示缩小时间段 |

## 3. 架构：编 / 生 / 渲 三层

```text
【编制层】需求 → 一份 composition（HTML）
   一个 segment（台词/镜头）= 一个容器，挂载：
   ├─ <video data-media-start data-start data-track-index>  真实素材 / AI 生成素材
   ├─ 字幕（captions，词级时间戳）
   └─ 包装（CSS + GSAP 动效）
         ↓ 语义锚定：删一句台词，挂它的镜头/字幕/音轨一起走
【生成层】编制时发现缺素材 → 调已有 atlascloud_video 工具补齐
         （过场 / 一致性修正帧；素材也可从知识库 P3 取料）
         ↓
【渲染层】hyperframes render → MP4 → 落 COS → 对话框预览
```

### 3.1 为什么 HyperFrames 能统一两条思路

实测确认 HyperFrames 原生具备以下能力（非推测）：

| 能力 | 属性 | 用途 |
| --- | --- | --- |
| 裁切源素材 | `data-media-start`（Trim offset into source） | 剪真实素材 |
| 时间轴定位 | `data-start`（秒或 clip ID 引用，如 `"intro + 2"`） | 编排 |
| 多轨叠加 | `data-track-index` | 画中画 / 字幕轨 |
| 音轨混音 | `data-volume` | 配乐 |
| 双画幅 | `data-width` / `data-height`（明确列 1920x1080 与 1080x1920） | 竖横屏 |
| 字幕 | 完整 captions 指南（词级时间戳、逐词样式） | 字幕 |
| 变量化重渲染 | `data-composition-variables` + `--variables` | 批量出变体 |

**因此「剪辑真实素材」与「代码渲染」不是两套系统**：真实素材是 `<video>` 片段，AI 生成素材是另一个片段，同一时间轴按 `data-start` / `data-track-index` 排布；语义锚定天然落在 HTML 容器层级上。

### 3.2 渲染宿主

HyperFrames 硬依赖 **Chromium + ffmpeg + Node（>= 22）**。现状核实：

| 事实 | 结论 |
| --- | --- |
| 主 api 镜像（`api/Dockerfile`） | 装了 `nodejs npm`，**无 ffmpeg、无 Chromium** |
| `api/Dockerfile.worker` | 已叠加 **playwright + xvfb**，是现成的浏览器渲染底座 |
| Celery 能力 | `visibility_timeout` 24h、无 `task_time_limit`、`acks_late` 有先例 → **支持长任务** |
| 现有队列消费 | 未传 `-Q` 时消费全部已声明队列（实测 Celery 5.6.3 `Queues.consume_from`） |

**方案**：复用 `Dockerfile.worker` 底座，新增 **`render` 队列 + 独立 Celery worker（显式 `-Q render`）**。

> **注意**：现有 worker 启动未传 `-Q`，意味着所有声明的队列都由同一 worker 消费。新增 `render` 队列**必须显式 `-Q`**，否则分钟级渲染会与业务任务争抢 worker，拖慢主链路。这不是既有缺陷（当前三个队列都被正常消费），而是本次新增必须做的隔离。

## 4. 成品入库与分类拆分

### 4.1 为什么用「系统预置成品库」而非新增 `base_type`

`base_type` 是板块的组织类型（mixed/video/...），用户可在建库时自由选择。而成品需要的是**确定的、唯一的、系统托管的**归集处——用户不应能随手建多个「成品库」。

```text
用户的 user_content 知识库
├── [零散素材库]  用户自建（base_type=mixed/video/...）
│     └─ 分区树、标签…（原料仓，用户自由组织）
└── [成品库]      系统预置唯一（created_from 标识）
      └─ 渲染产物自动写入（成品仓，由渲染链路写入）
```

**关键性质**：

- 成品库走**同一套 P3 检索**（分区/媒体类型/标签/相似度阈值），所以「可复用」天然成立——用户可让小钰从成品库翻旧片翻新。
- **禁止手动上传**：上传入口对该库直接拒绝，保持「成品」语义纯净。
- 与零散素材**彻底分开**：靠库归属区分，不在同一板块内混放。

### 4.2 预置时机

首次需要写成品时**幂等创建**（`get_or_create`），避免给从未出片的用户平白建库。并发创建需靠唯一约束兜底（同一账号下成品库唯一）。

## 5. 分层动态抽帧（L1 / L2）

### 5.1 现状缺陷（已核实）

`_extract_frames_to_dir` 调用 `extract_video_frames_to_dir(video_path, out_dir)` **不传 `frame_count`**，使用默认 `_DEFAULT_FRAME_COUNT = 3`。ffmpeg 命令：

```python
"-vf", "select='not(mod(n\\,100))'",   # 每 100 帧取 1 帧
"-frames:v", str(frame_count),          # 硬上限 3
```

**后果**：无论视频多长都只抽开头的 3 帧。

| 视频 | 实际抽帧 |
| --- | --- |
| 10 秒 | 前 3 帧（约 0/3.3/6.7 秒） |
| 1 小时 | 前 3 帧（约 0/3.3/6.7 秒） |
| 10 GB | 前 3 帧 |

这直接导致 P4「改细节」不可行——系统只知道开场 7 秒长什么样。**且帧 metadata 无时间偏移**，即使抽了也无法定位。

### 5.2 L1：全片粗索引（目标「能被找到」）

**帧数随时长对数增长**，1 小时触顶：

```text
frames = clamp(round(8 · log2(duration_sec) − 35), min=6, max=60)
```

实测校验（已跑数验证）：

| 时长 | L1 帧数 | 间隔 |
| --- | --- | --- |
| 10 秒 | 6 | 1.7s |
| 1 分钟 | 12 | 5.0s |
| 5 分钟 | 31 | 9.7s |
| 30 分钟 | 52 | 34.6s |
| **1 小时** | **60** | **60.0s（触顶）** |
| 2 小时 | 60 | 120.0s（封顶） |

> **实现要求**：去掉 `-frames:v` 的「从头截断」语义，改为**按 duration 计算采样间隔**并全片均匀取帧（`-ss` 定位或按总帧数算 step），而非写死 `mod(n,100)`。

### 5.3 新增 `time_offset`（前置依赖）

帧片段 `metadata` 现仅有 `scene_index`。必须新增 **`time_offset`（该帧对应视频第几秒）**：

| 用途 | 说明 |
| --- | --- |
| L1 定位 | 帧片段知道自己对应视频第几秒 |
| L2 扩抽 | 按时间段 `-ss <start> -t <span>` 密集抽 |
| 取料结果 | 设计稿 §4.2 要求「带时间戳」 |

**这同时补上了设计稿 §4.2 写的 `metadata.time_range`**——该能力一直是「设计有、代码无」。

### 5.4 L2：区间密集（目标「能被精细修改」）

**L2 不重扫全片，而是三步**：

```text
1. 定位：复用 L1 已建索引，检索命中帧带 time_offset → 得到目标时刻
2. 扩窗：命中时刻 ± 前后留白（默认 ±10s）；多个命中则合并重叠窗口
3. 密抽：仅在该窗口内按 0.5 秒 1 帧抽帧 → 逐帧详述 → 回写/新增 Segment
```

**L1 与 L2 的分工**：L1 是**粗地图**（能被搜到、能定位），L2 是**放大镜**（对搜到的位置看清细节）。若无 L1，L2 就退化成「重扫全片」，成本失控且 L1 失去意义。

**成本对比**（视觉模型调用次数）：

| 场景 | 重扫全片（错误做法） | 按窗口密抽（本设计） |
| --- | --- | --- |
| 1 小时视频改 20 秒片段 | 7,200 次 | **40 次** |

**单次窗口上限 600 帧**（= 5 分钟）：超出提示「请缩小时间段」。作用是挡住「对长视频整段触发 L2」的极端请求。

### 5.5 连带影响

- L2 密抽产生**新帧文件**（非仅改写 L1 帧），故 L2 **也吃配额**，且同一文档帧数随每次 L2 累积增长。这是「按需付费」的合理形态，但需在用量面板可见。
- **前向风险**：若未来把 L1 改成「按场景密集抽帧」（帧数随时长线性增长），则 5.6 的配额上界模型失效，需改为「帧数上限 × 单帧上限」动态计算。

### 5.6 解析开销的配额上界（实测得出）

实测（真实抽帧代码，`testsrc` 合成源）显示：**帧开销是绝对量，与源大小无关**——同为 1080p，源从 0.05MB 到 9.80MB，每帧字节几乎不变（60.0KB → 60.1KB），因为抽帧是「固定帧数 + 原生分辨率 + JPEG 压缩」。

| 分辨率 | 每帧 | 3 帧合计 |
| --- | --- | --- |
| 360p | 10 KB | 31 KB |
| 720p | 23 KB | 70 KB |
| 1080p | 40–60 KB | 120–180 KB |
| 4K | 110 KB | 331 KB |

> **重要修正**：曾假设「2G 素材解析后 2.2G（+10%）」，实测为 **+0.006%**（固定 3 帧时）。倍数模型不成立（实测倍率跨度 0.0024 ~ 2.667，超 1000 倍）。故**放弃倍率，改用帧数上限 × 单帧上限**。

**配额预留公式**：

```text
L1 解析预留 = L1帧数上限(60) × 单帧上限(最坏 4K 110KB) ≈ 6.6 MB
```

> **保留意见**：实测用 ffmpeg `testsrc` 合成源；真实拍摄画面（自然纹理、噪点）JPEG 体积可能更大，故 6.6MB 已含余量。上线后若实测超界，调整这一个常量即可。

## 6. 配额语义

现有 `StorageQuotaService` 已具备所需原语（`consume_quota` 行锁原子预占 / `release_usage` 释放 / `check_quota` 读校验），本设计是**在正确抽象上扩展**。

### 6.1 计费判据：是否堆积

| 产物 | 生命周期 | 计配额 |
| --- | --- | --- |
| **关键帧 `UploadFile`** | 持久化（落 COS + `upload_file` 落库） | ✅ 计入 |
| 音轨 wav | `TemporaryDirectory` + `os.remove` | ❌ |
| 抽帧中间文件 | `TemporaryDirectory` 自动回收 | ❌ |
| L2 详述 / ASR 文本 | 改写既有 Segment 内容，不新增文件 | ❌ |
| 视觉向量 | pgvector 行，不在对象存储口径 | ❌ |

> **反转 P3 决定**：P3 文档写的是「帧留存不计配额」，本设计**有意改为计入**（帧是持久化产物，符合「堆积即计费」判据）。文档需同步修正。

### 6.2 必须成对修复的连带缺陷

核实发现：帧的 `upload_file` 记录**当前既不计费、也永不清理**（`purge_knowledge_document` 只删 `snapshot["upload_file"]` 主文件，不删帧文件）——已是孤儿。一旦改为计费，就会变成**配额泄漏**（用户删素材后帧仍在，扣掉的空间永不归还）。

**故本项必须成对实现：计费 + 释放**（`purge_knowledge_document` 需同时清理帧文件并 `release_usage`）。

### 6.3 两种模式

| | 素材上传（严格） | 成品入库（宽让） |
| --- | --- | --- |
| 校验量 | 素材大小 + **解析预留**（§5.6） | 仅成片大小 |
| 超限行为 | **拒绝**，报 `storage_quota_exceeded` | **允许溢出** |
| 触发条件 | 每次上传 | 仅当 `remaining > 0` |
| 恰好剩余 0 | 拒绝 | **拒绝**（一丝不多不少也不放行） |
| 溢出后 | — | 立即超额，后续上传全拒；扩容后溢出部分吃掉新容量（网盘式） |

**为什么成品宽让**：成品由系统写入，若因配额差一点而失败，会导致**整轮渲染白干**。故允许溢出；但「仅当剩余 > 0」这道闸防止已超额用户无限产片。

> **存量数据**：帧不追溯补扣（当前为纯开发环境，无存量顾虑）。

## 7. 涉及反转 P3 已落地行为的清单

| 项 | P3 现状 | 本设计改动 |
| --- | --- | --- |
| L1 抽帧 | 固定 3 帧、只取开头 | 动态 6–60 帧、全片均匀 |
| 帧 metadata | 仅 `scene_index` | **+ `time_offset`** |
| L2 语义 | 重描述 L1 那几帧 | 区间内 0.5s/帧密集抽 |
| 帧配额 | 不计 | **计入**（+ 补齐释放逻辑） |
| L2 帧文件 | 不产生 | 产生，累积增长 |

| 复用 | 位置 | 用途 |
| --- | --- | --- |
| 视频生成工具 | `atlascloud_video` provider（13 个工具：Seedance 2.0 / Hailuo 2.3 / Kling O3 / Vidu Q3） | 生成层补齐过场/一致性素材 |

> **接线要求（AGENTS.md 强制规则）**：新增的 Celery 任务必须同时具备 `TASK_MODULES` 登记**与派发点**；新增 builtin 工具必须同时具备 `.py` + `.yaml` + `providers.yaml` 登记 + **运行时挂载点**；新迁移的 `down_revision` 必须指向已提交的迁移。

## 9. 风险与未决项

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| HyperFrames 版本演进 | 依赖 `npx hyperframes`，版本漂移可能改变行为 | 锁定版本；渲染 worker 镜像固定依赖 |
| 单帧上限为合成源测得 | 真实画面 JPEG 可能更大 | 预留已含余量；上线后实测校准该常量 |
| L2 场景切分未实现 | 本设计的 L2 按时间窗口密抽，非按场景 | 场景切分（`select='gt(scene,...)'`）列为后续增量 |
| 渲染产物成本 | 成片 + 帧 + 模型调用 | 配额已覆盖存储；模型调用走 `public_ai_feature_config` |
| 渲染是长任务 | 分钟级 | 独立 `render` 队列 + `-Q` 隔离 |

## 10. 验收要点

| 能力 | 可独立验证 |
| --- | --- |
| L1 动态抽帧 | 10 秒视频抽 6 帧、1 小时抽 60 帧；帧分布覆盖全片而非仅开头 |
| `time_offset` | 帧片段 metadata 含正确时间偏移；检索结果可据此定位 |
| L2 区间密抽 | 命中 20 秒区间只抽约 40 帧（非 7200 帧）；600 帧上限生效 |
| 成品入库 | 出片后自动入成品库；成品库出现在该用户库列表且可被检索 |
| 成品库禁止上传 | 向成品库上传素材被拒 |
| 素材配额严格 | 剩余不足（含解析预留）时上传被拒并提示扩容 |
| 成品配额宽让 | 剩余 > 0 时超量成片可入库；剩余 = 0 时拒绝 |
| 帧配额对账 | 删除素材后帧文件与用量一并释放，`used_bytes` 无泄漏 |
| 渲染隔离 | `render` 队列任务不影响主业务队列 |
